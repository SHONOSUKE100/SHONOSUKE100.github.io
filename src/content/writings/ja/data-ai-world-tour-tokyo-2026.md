11月27日に、Databricks のイベント「Data + AI World Tour Tokyo」に行ってきました。会場は東京・芝公園のザ・プリンス パークタワー東京です。前の日には [Architecture Conference 2026](/ja/writing/architecture-conference-2026/) に参加していたので、2日続けてのカンファレンスになりました。

いま私は、CMU のデータベースの講義（15-445/645）を独学しています。せっかくなので今回は、新しい製品の機能そのものより、「中で何が起きているのか」をデータベースの内部の視点で考えながら聞くことにしました。この記事では、そのとき考えたことも含めてまとめます。

先にまとめると、この日いちばん印象に残ったのは、Databricks の製品の多くが同じ方針で作られていることです。

> データは1か所に置き、使い道ごとにエンジンを分ける。データを別のシステムへコピーしない。

なお、製品の数値や仕様は講演と公式の情報にもとづいています。「私の推測」と書いた部分は、公式の説明ではなく自分の考えです。

## 基調講演：1つのデータの上に、いくつものエンジン

基調講演では、新しい製品や機能がまとめて紹介されました。主なものは次のとおりです。

| 名前 | ひとことで言うと |
| --- | --- |
| Lakeflow | データの取り込み、変換、ジョブの実行をまとめたデータエンジニアリング基盤 |
| Genie ZeroOps | 本番のパイプラインやテーブルを見張り、異常の原因と直し方を提案するエージェント。人が承認してから適用する |
| Lakebase | Databricks のマネージド Postgres。アプリのトランザクション処理（OLTP）を担う |
| Lakehouse//RT | レイクのテーブルにミリ秒単位で答える、リアルタイム分析用のエンジン |
| Genie Ontology | 「売上」「顧客」のような業務の意味を、テーブルや列と結びつける層 |

Genie Ontology の話は、前の日の Architecture Conference で聞いた NTT ドコモのデータメッシュの話と重なっていました。どちらも、AI にデータを正しく使わせるには、データそのものだけでなく「そのデータが業務で何を意味するか」という文脈が要る、という問題意識です。Databricks の場合は、人がメトリクスや用語集を定義する層（Unity Catalog Semantics）を土台にして、Genie Ontology がそれを取り込み、実際の使われ方からも学習して文脈を広げていく、という構成でした。

リアルタイム分析の話では、「レイテンシとスループットの両方が大事で、スループットの限界を超えるとシステムは崩れる」という説明があり、Lakehouse//RT は 12,000 QPS（1秒あたりのクエリ数）でもレイテンシを 100 ms 未満に保てる、と紹介されていました。この2つの製品は、午後のセッションで詳しく聞きました。

## Lakebase と LTAP：OLTP と分析をつなぐ方法

午後最初のセッションは、この日いちばん楽しみにしていた Lakebase と LTAP の話です。

### Lakebase は「ストレージと計算を分けた Postgres」

Lakebase の名前は、Lake（ストレージ）と Base（データベースのエンジン）を組み合わせたものだそうです。中身は、Databricks が買収した Neon のアーキテクチャをもとにしています。

ふつうの Postgres は、1台のサーバーの中で、クエリの実行も、ログ（WAL）の書き込みも、データページの保存もこなします。Lakebase では、この役割が別々のコンポーネントに分かれています。

| 役割 | ふつうの Postgres | Lakebase |
| --- | --- | --- |
| クエリの実行 | サーバー上の Postgres | ステートレスな Postgres（Compute） |
| WAL の永続化 | ローカルディスク | Safekeeper（複数台で合意をとって保存） |
| データページの保存 | ローカルディスク | Pageserver（WAL からページを組み立てる） |
| 長期の保存 | ローカルディスク | オブジェクトストレージ（S3 など） |

書き込みの流れは次のようになります。

1. Compute がトランザクションの WAL を作り、Safekeeper に送る
2. Safekeeper の過半数が WAL を保存した時点で、コミットが成立する
3. Pageserver が WAL を受け取ってページの形に組み立て、最終的にオブジェクトストレージに書き出す

Compute はローカルにデータを持たないので、すぐに起動・停止でき、使っていないときは0台まで縮められます。ストレージはコピーオンライトなので、データベースのブランチ（コピー）を一瞬で作れ、過去の時点にも戻せます。

15-445 の言葉でいえば、Compute 側に残っているのはバッファプール（Shared Buffer と、その下のローカルキャッシュ）で、ディスクの代わりにネットワークの向こうの Pageserver があるイメージです。

### LTAP：運ぶのではなく、ストレージで変換する

LTAP は Lake Transactional/Analytical Processing の略です。OLTP のデータを分析に使うときの、新しいつなぎ方として紹介されました。

これまでは、CDC（変更データキャプチャ）で OLTP のデータベースから変更を取り出し、Kafka などのパイプラインを通して分析基盤へ運ぶのが定番でした。ただ、パイプラインの運用、遅延、スキーマ変更への追従、データの二重保存と、手間のかかる部分が多くあります。

LTAP では、データを運びません。Pageserver が Postgres のページをオブジェクトストレージに書き出すついでに、行指向のページを列指向の Parquet に変換します。こうしてできたデータは Delta や Iceberg のテーブルとして、ほかの分析エンジンからそのまま読めます。講演によると、変換は可逆で、Parquet から元の Postgres のページを組み立て直すこともできます。公式ブログでは、各行がヒープのブロック番号、オフセット、MVCC のバージョンを持っていて、Parquet のほうが正本、ヒープページはそのキャッシュという位置づけだと説明されています。

OLTP と分析をつなぐ方式を、自分なりに比べてみました。

| | HTAP（TiDB など） | Zero-ETL（Aurora → Redshift） | LTAP（Lakebase） |
| --- | --- | --- | --- |
| 何をひとつにするか | エンジン | 同期の運用 | ストレージ |
| 列指向のデータの作り方 | 列ストアのレプリカがログを受けて反映する | 分析用の DB に複製する | ページの書き出し時に Parquet に変換する |
| 分析に使えるエンジン | 専用のエンジン | 専用のエンジン | Delta / Iceberg を読めるエンジンなら何でも |

### 私が考えたトレードオフ

講演を聞きながら、データベースの内部の視点で気になった点を挙げておきます。ここは私の推測です。

- **並び順と読み飛ばし**：Parquet はヒープページの順に並ぶので、日付などで範囲を絞る分析では、min/max の統計を使った読み飛ばしが効きにくいはずです。公式ブログでもこの点は認めていて、分析しやすい並びに直したテーブルを別に作ることを勧めていました。
- **書き込みの増幅**：同じデータが WAL、ページ、Parquet と3回書かれ、保存も行と列の2つの形になります。
- **単一の書き込みノード**：1つのブランチに書き込める Compute は1台です。書き込みのスケールは、Spanner や CockroachDB のような分散データベース（NewSQL）とは違い、1台の性能が上限になります。Lakebase が解こうとしているのは書き込みのスケールではなく、弾力性、コスト、ブランチ、レイクとの統合のほうだと理解しました。
- **「コピーが1つ」の意味**：物理的には行と列の2つの形がありますが、正本となる論理的なデータは1つ、という意味です。

LTAP はまだ提供前（coming soon）とのことでした。実際に使えるようになったら、コミットしてから分析で見えるまでの遅延や、更新の多いテーブルでの性能を確かめてみたいです。

## Turing：自動運転 AI を支える MLOps 基盤

次は、完全自動運転を開発している Turing のセッションです。ここで聞いた話は、データエンジニアリングとしてとても実践的でした。

### End-to-End の自動運転と、データの重要性

従来の自動運転は、認識、予測、計画、制御の4つのモジュールに分かれ、高精度な地図とルールベースの判断に頼っていました。Turing はこれを、カメラ画像から運転の判断までを1つのニューラルネットでつなぐ End-to-End のモデルに置き換えています。さらにその先として、言語モデルを拡張したフィジカル基盤モデルを車に載せる方向も目指しているそうです。

End-to-End のモデルは、性能がデータの量と質で決まります。歩行者、自転車、工事の作業員などが入り混じる日本の道路や、死角からの飛び出しのような見通しの悪い場面は、ただ走っているだけではなかなか集まりません。そこで、モデルの弱点から逆算して「次にどんなデータを集めるか」を決め、そのシーンが出るように走行ルートまで計画しているそうです。モデルは1日に5〜10個作っているとのことでした。

### データの流れ

データ収集から車への搭載までの流れのうち、Databricks を使っているのはデータの準備の部分です。

```text
データ収集 → 標準化 → 選定 → 学習 → 評価 → 車へデプロイ
             └ Databricks ┘
```

車から届いた映像やセンサーのログは、そのまま S3 に置きます。メタデータ、映像の説明文（キャプション）、似たシーンを探すための埋め込みベクトルといった「データについてのデータ」は、ストリーミングで Lakehouse のテーブルに入れて管理します。ETL は Lakeflow の宣言的パイプラインで書いていて、次々に届くログの取り込みには Streaming Table、集計や抽出には Materialized View と使い分けていました。

学習用のデータセットは、このパイプラインとは別のジョブとして作ります。入力は CSV と設定ファイル（YAML）だけです。共通の ETL と実験ごとのデータセット作りを切り離しているので、パイプラインに触らずにデータセットを量産できます。データセットの定義がファイルとして Git に残るので、「このモデルはどのデータで学習したか」もたどれます。

### うまいと思った工夫

講演で紹介された工夫の中から、特に面白かったものを挙げます。

- **動画のまま保存し、学習のときにデコードする**：以前は動画をフレームごとの画像にして保存していましたが、容量が5〜10倍に増え、学習ノードへの転送のコストもかかっていました。今は圧縮された動画のまま保存し、学習時に NVIDIA の GPU のデコーダで画像に戻しています。データセットごとに動画をコピーせず、共有して重複を減らしているそうです。
- **学習しやすい形にデータを作り直す**：以前は自動運転の公開データセット nuScenes と同じ形式を使っていました。これは、センサーやアノテーションごとにテーブルが分かれ、ID で参照し合う正規化された形式です。拡張しやすい反面、学習の1サンプルを組み立てるたびに多くのテーブルをたどる必要がありました。今は、1サンプルを1レコードにまとめた独自の形式に変え、読み込みを速くしています。
- **main にマージしなくても試せる**：ジョブやパイプラインの定義を YAML でコードと一緒に管理し（Declarative Automation Bundles）、開発中のブランチを本番と同じ Spark クラスタで動かせるようにしています。以前は開発をローカルのマシンでしていたので、本番の規模で初めて出る問題に気づけませんでした。
- **ゴールデンデータで回帰を確かめる**：正しいと確認済みの出力（ゴールデンデータ）を用意しておき、CI でパイプラインの出力と比べています。
- **コーディングエージェントが変更しやすい単位にする**：処理を共通の `PipelineStep` クラスを継承したステップとして書いています。1ステップの入出力がはっきりしているので、エージェントにも変更を任せやすく、レビューもしやすくなります。

### データベースの視点で見ると

この講演は、データベースの授業で習う話の実例だらけでした。

- nuScenes 形式から1レコード1サンプルへの変更は、まさに**正規化と非正規化のトレードオフ**です。学習データは一度書いたら何度も読まれるので、結合のコストをデータセット作成時に一度だけ払うほうが合理的です。
- 動画を圧縮したまま保存して読むときに展開するのは、**容量と計算のトレードオフ**で、列指向ストレージの圧縮と同じ発想です。
- Materialized View を元データの変更に合わせて更新するのは、**ビューの増分更新（IVM）**の問題です。
- サーバーレスで「失敗すると自動でリトライされる」という制約の話もありました。私の推測ですが、これに耐えるには処理を**冪等**にする必要があります。少なくとも1回は実行され、何度実行しても結果が同じなら、実質的に1回だけ実行したのと同じになります。

## Lakehouse//RT：コピーせずにリアルタイム分析をする

最後に聞いたのは、Lakehouse//RT のセッションです。

### リアルタイム分析の3つの指標

講演では、リアルタイム分析で大事な指標として、次の3つが挙げられました。

| 指標 | 意味 |
| --- | --- |
| データの鮮度 | データが生まれてから、クエリで見えるようになるまでの時間 |
| 応答時間 | 1つのクエリが返るまでの時間 |
| 同時実行性能 | 同時にさばけるクエリの数（QPS） |

これまでは、Lakehouse からデータをコピーして、ClickHouse のようなリアルタイム分析用の別のシステムを用意するのが一般的でした。ただ、この方法には、データが重複する、Unity Catalog の権限や来歴がコピー先に効かずガバナンスが分断される、コピーの仕組みの保守で開発が遅くなる、という課題があります。Lakehouse//RT は、Delta や Iceberg のテーブルをコピーせずにそのまま読み、低レイテンシで答えることでこれを解こうとしています。

### 数字

講演で示された数字は次のとおりです。

- 最小のレイテンシは 10 ms
- 1秒あたり 12,000 クエリ
- 横長の1テーブルに集計クエリを流すベンチマーク ClickBench で 2.8 倍、複数のテーブルを結合するデータで約3倍の高速化

何と比べた数字なのか、どんな条件で測ったのかは、聞き取れませんでした。ベンダーの公称値なので、その前提で受け取っています。個人的に面白かったのは、結合ありでも速いという点です。リアルタイム分析用のデータベースは結合が苦手なことが多く、事前にデータを横長のテーブルにまとめてからコピーする運用になりがちです。結合のまま速いなら、その非正規化のコピーも要らなくなります。

なお、Lakehouse//RT は読み取り専用で、長時間のスキャンやバッチ ETL には向かないと説明されていました。役割は、ダッシュボードやアプリから来る短いクエリを大量にさばくことです。

### なぜ速くできるのか（私の推測）

講演を聞きながら、「なぜ Spark のような分散エンジンでは同じことができないのか」「Lakehouse//RT はどうやっているのか」を考えていました。以下は私の推測です。

Spark のようなエンジンは、大量のデータを効率よく処理するスループット重視の設計です。1つのクエリでも、実行計画を作り、ステージやタスクに分け、各ノードに配り、結果を集める、という段取りがあります。この固定のオーバーヘッドだけで数百 ms はかかります。さらに、1つのクエリをクラスタ全体に広げて速くする設計なので、同時に多くのクエリが来ると資源の奪い合いになります。

規模感はリトルの法則でつかめます。同時に動いているクエリの数は「QPS × 1クエリの時間」なので、12,000 QPS で1本 10〜100 ms なら、常に 120〜1,200 本のクエリが同時に動いていることになります。1本を速くするだけでなく、1本あたりが使う資源を小さくして大量に並べることが本質のはずです。

そのために効きそうなのは、次のような工夫です。

1. **キャッシュでオブジェクトストレージを避ける**：S3 への1回のアクセスには数十 ms かかるので、10 ms を出すにはクエリの途中で S3 を読まないことが前提になります。ドキュメントには、テーブルのメタデータをキャッシュするため最新のコミットから数秒遅れることがある、と書かれていて、この推測と合っています。データ本体もメモリやローカル SSD にキャッシュしているはずです。バッファプールと同じ発想です。
2. **1本のクエリを小さく保つ**：短いクエリは1つのノードで最後まで処理し、ノード間でデータを交換しない。これで、遅いノードに全体が引きずられることも避けられます。
3. **読み取り専用であることを活かす**：書き込みがないので、ロックもトランザクションの調整も要りません。同じデータを読むノードを増やすだけで、QPS をほぼ比例して伸ばせます。
4. **クエリごとの固定費を削る**：ダッシュボードやアプリからのクエリは、パラメータが違うだけで形は同じことがほとんどです。実行計画のキャッシュや、統計情報を使ったファイルの読み飛ばしが効きます。

### データは1か所、エンジンは複数

1日を通して聞くと、Databricks が同じレイクのデータに対して、用途ごとにエンジンを分けていることがよく分かりました。

| エンジン | 用途 | 何を最適化しているか |
| --- | --- | --- |
| Lakebase | OLTP（書き込み、トランザクション） | 1行の読み書きの速さ |
| Spark / Lakeflow | バッチ ETL、変換 | スループット |
| Databricks SQL | 対話的な分析、BI | スキャンの速さ |
| Lakehouse//RT | ダッシュボードやアプリへの提供 | レイテンシと同時実行性能 |

LTAP は「OLTP から分析へのコピー」をなくし、Lakehouse//RT は「分析からリアルタイム提供へのコピー」をなくします。向きは違っても、どちらも同じ方針の上にあります。

## 楽天の事例：AI がデータを書く時代のガバナンス

楽天の講演では、Iceberg を中心にしたデータ基盤と、AI のガバナンスの話がありました。AI がデータを読むだけでなく書くようにもなり、ガバナンスを強める必要が高まっている、という問題意識です。

課題として挙げられていたのは、次の4つが足りないことでした。

1. 誰が、どのモデルやエージェントを、どれだけ使っているかの可視化
2. エージェントが中で何をしたかを追えるオブザーバビリティ
3. 危険な入出力を止めるガードレール
4. アクセス制御

その答えとして紹介されたのが Unity AI Gateway です。データの資産は Unity Catalog で、モデル、エージェント、MCP サーバーなど AI の資産の実行は Unity AI Gateway で管理し、この2つで統合的なガバナンスを実現する、という構成でした。

聞きながら考えていたのは、AI エージェントの権限を「エージェントに付けるか、使う人に付けるか」という問題です。前の日の Architecture Conference でも、エージェントに固有の ID を与えて最小権限の原則を当てはめる話がありました。人の代わりに動くチャット型のエージェントなら人の権限で、人が介在しない定期実行のエージェントなら専用の ID で、というように使い分けるのが現実的だと思います。

## おわりに

製品の発表を聞きに行ったつもりが、データベースの授業の復習をしているような1日でした。ストレージと計算の分離、WAL と合意、行指向と列指向、正規化と非正規化、キャッシュ、ビューの増分更新。どれも 15-445 で出てくる概念で、それが実際の製品の中でどう組み合わされているのかを考えるのは、とても楽しい時間でした。

特に、「データは1か所に置き、エンジンを分ける」という方針は、前の日の Architecture Conference で聞いたデータメッシュやゼロコピーのデータ共有の話ともつながっていて、2日間を通して1つの流れが見えた気がします。
