*会場の近くから見た東京タワーとイチョウ*

いま私は、CMU のデータベースの講義（15-445/645）を独学しています。データベースやデータ基盤の新しい動きを知りたくて、今回のイベントは前から楽しみにしていました。

この記事では、聞いたセッションの内容と感想をまとめます。それぞれの技術の中身は面白いところが多かったので、別の記事で改めて掘り下げるつもりです。

## 基調講演

基調講演では、新しい製品や機能がまとめて紹介されました。主なものは次のとおりです。

| 名前 | ひとことで言うと |
| --- | --- |
| Lakeflow | データの取り込み、変換、ジョブの実行をまとめたデータエンジニアリング基盤 |
| Genie ZeroOps | 本番のパイプラインやテーブルを見張り、異常の原因と直し方を提案するエージェント。人が承認してから適用する |
| Lakebase | Databricks のマネージド Postgres。アプリのデータベースを担う |
| Lakehouse//RT | 分析用のテーブルに、ミリ秒単位で答えるリアルタイム分析のエンジン |
| Genie Ontology | 「売上」「顧客」のような業務の意味を、テーブルや列と結びつける仕組み |

印象に残ったのは Genie Ontology です。前の日の Architecture Conference で聞いた NTT ドコモのデータメッシュの話でも、オントロジーで業務の用語とデータを結びつける話がありました。AI にデータを正しく使わせるには、データそのものだけでなく「そのデータが業務で何を意味するか」という文脈が要る。2日続けて、同じ問題意識に出会いました。

## Lakebase：アプリのデータベースを、分析の基盤の上に

午後最初のセッションは、この日いちばん楽しみにしていた Lakebase の話です。

Lakebase は、Databricks が提供する Postgres です。Databricks が買収した Neon の技術をもとにしていて、データの保存と計算を分けているのが特徴です。そのおかげで、使っていないときは計算資源をゼロまで縮められ、データベースのコピー（ブランチ）も一瞬で作れます。

あわせて紹介されたのが LTAP という仕組みです。これまで、アプリのデータベースにあるデータを分析に使うには、変更を取り出して分析用の基盤へ運ぶパイプラインを作るのが一般的でした。LTAP では、Lakebase が保存するデータを、分析に向いた形式（Parquet）にも自動で変換します。データを運ばなくても、分析のエンジンからそのまま読めるようになります。LTAP はまだ提供前（coming soon）とのことでした。

アプリのデータと分析のデータをどうつなぐかは、データ基盤でいつも悩みどころになる部分です。それを「運ぶ」のではなく「保存の段階で両方の形にする」という発想が面白く、講義で学んでいる行指向と列指向の違いが、こんな形で製品になるのかと感じました。

## Turing：自動運転 AI を支える MLOps 基盤

次は、完全自動運転を開発している Turing のセッションです。

Turing は、カメラの映像から運転の判断までを1つのニューラルネットでつなぐ、End-to-End の自動運転モデルを開発しています。このやり方では、モデルの性能がデータの量と質で決まります。そこで、モデルの弱点から逆算して次に集めるデータを決め、そのシーンが出るように走行ルートまで計画しているそうです。モデルは1日に5〜10個作っているとのことでした。

Databricks は、集めた走行データを学習に使える形に整える部分で使われていました。印象に残った工夫をいくつか挙げます。

- **動画のまま保存する**：以前は動画をフレームごとの画像にして保存していましたが、容量が5〜10倍に増えていました。今は動画のまま保存し、学習のときに GPU で画像に戻しています。
- **設定ファイルだけでデータセットを作れる**：学習用のデータセットは、CSV と YAML の設定ファイルを渡すだけで作れるようにしています。データセットの定義がファイルとして残るので、「どのモデルがどのデータで学習したか」もたどれます。
- **正解のデータと比べてテストする**：正しいと確認済みの出力を用意しておき、パイプラインを変更したら CI で出力を比べています。
- **AI エージェントにも変更しやすい形にする**：処理を、入力と出力がはっきりした小さなステップに分けて書いています。コーディングエージェントに変更を任せやすく、レビューもしやすくなります。

自動運転というと、モデルそのものに目が行きがちです。ただ、このセッションで語られていたのは、データを集め、整え、何度でも学習を回せるようにする仕組みのほうでした。モデルを速く改善できるかどうかは、データ基盤の作りで決まるのだと実感しました。

## Lakehouse//RT：コピーせずにリアルタイム分析をする

最後に聞いたのは、Lakehouse//RT のセッションです。

ダッシュボードやアプリでリアルタイムに分析結果を見せたいとき、これまでは分析用のデータを ClickHouse のような別のシステムにコピーするのが一般的でした。ただ、この方法には、データが二重になる、権限の管理が分断される、コピーの仕組みの保守に手間がかかる、という課題があります。

Lakehouse//RT は、分析用のテーブルをコピーせずにそのまま読み、ミリ秒単位で答えることを目指したエンジンです。講演では、最小のレイテンシが 10 ms、1秒あたり 12,000 クエリをさばける、という数字が紹介されていました（ベンダーの公称値です）。読み取り専用で、大量のデータを読み切るバッチ処理ではなく、短いクエリを大量にさばく用途に向いている、という位置づけでした。

## 楽天：AI がデータを書く時代のガバナンス

楽天の講演では、AI がデータを読むだけでなく書くようにもなり、ガバナンスを強める必要が高まっている、という話がありました。課題として挙げられていたのは、次の4つが足りないことです。

1. 誰が、どのモデルやエージェントを、どれだけ使っているかの可視化
2. エージェントが中で何をしたかを追える仕組み
3. 危険な入出力を止めるガードレール
4. アクセス制御

その答えとして紹介されたのが Unity AI Gateway です。データは Unity Catalog で、モデルやエージェントといった AI の利用は Unity AI Gateway で管理する、という構成でした。

前の日の Architecture Conference でも、AI エージェントに固有の ID と権限を与える話がありました。AI に仕事を任せるほど、「誰が、何を、どこまでしてよいか」を決める仕組みが大事になる。2日間を通して、そう感じました。

## おわりに

1日を通して印象に残ったのは、Databricks の製品の多くが同じ方針で作られていることです。

> データは1か所に置き、使い道ごとにエンジンを分ける。データを別のシステムへコピーしない。

アプリのデータベース（Lakebase）、バッチ処理、対話的な分析、リアルタイム分析（Lakehouse//RT）と、用途ごとにエンジンを用意し、どれも同じデータを読む。LTAP や Lakehouse//RT は、これまで当たり前だった「データのコピー」をなくすための仕組みでした。

また、ストレージと計算の分離、行指向と列指向、キャッシュといった、いま講義で学んでいる概念が、実際の製品の中で次々に出てきたのも楽しい体験でした。製品の発表を聞きに行ったつもりが、データベースの授業の続きを聞いているような気分になる場面もありました。

それぞれの技術の中身については、別の記事でじっくり調べて書いてみるつもりです。
