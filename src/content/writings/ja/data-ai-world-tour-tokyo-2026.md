11月27日に、Databricks のイベント「Data + AI World Tour Tokyo」に行ってきました。会場は東京・芝公園のザ・プリンス パークタワー東京です。前の日には [Architecture Conference 2026](/ja/writing/architecture-conference-2026/) に参加していたので、2日続けてのカンファレンスになりました。

![青空の下、黄色く色づいたイチョウの並木の向こうに東京タワーが見える](/images/writings/data-ai-world-tour-tokyo-2026/tokyo-tower.jpg)

*会場の近くから見た東京タワーとイチョウ*

いま私は、CMU のデータベースの講義（15-445/645）を独学しています。データベースやデータ基盤の新しい動きを知りたくて、今回のイベントは前から楽しみにしていました。

この記事では、聞いたセッションの内容と感想をまとめます。それぞれの技術の中身は面白いところが多かったので、別の記事で改めて掘り下げるつもりです。

## 基調講演

基調講演では、新しい製品や機能がまとめて紹介されました。主なものは次のとおりです。

| 名前 | ひとことで言うと |
| --- | --- |
| Lakeflow | データの取り込み、変換、ジョブの実行をまとめたデータエンジニアリング基盤 |
| Genie ZeroOps | 本番のパイプラインやテーブルを見張り、異常の原因と直し方を提案するエージェント |
| Lakebase | Databricks のマネージド Postgres。アプリのデータベースを担う |
| Lakehouse//RT | 分析用のテーブルに、ミリ秒単位で答えるリアルタイム分析のエンジン |
| Genie Ontology | 「売上」「顧客」のような業務の意味を、テーブルや列と結びつける仕組み |

Lakeflow は、SaaS やデータベースからの取り込み（Lakeflow Connect）、宣言的に書く ETL（Lakeflow Declarative Pipelines）、ジョブの実行管理（Lakeflow Jobs）などをひとまとめにしたものです。複雑になりがちなデータパイプラインを1つの基盤で扱い、ガバナンスはすべて Unity Catalog の下に置く、という説明でした。

Genie ZeroOps は、本番のジョブやテーブルを裏で見張り、データ品質の異常などを見つけると、原因を調べて直し方を提案するエージェントです。直し方を適用するのは、人が承認してから、という流れになっています。

一番印象に残ったのは Genie Ontology です。人が定義する「Unity Catalog Semantics」を土台にした、次のような層の構成でした。

- **Unity Catalog Semantics**：人が AI の手を借りながら定義する層。業務に沿ったデータの整理（Domains）、業務の概念と分類（Pages）、使い回せる KPI の定義（Metrics）からなる
- **Genie Ontology**：Semantics に加えて、データやアプリ（Slack やメールなど）から自動で学習した知識を組み合わせ、組織全体の文脈として提供する層
- **使う側**：Genie、MCP、SQL、API、ダッシュボードなど、どこからでもこの文脈を使える

前の日の Architecture Conference で聞いた NTT ドコモのデータメッシュの話でも、オントロジーで業務の用語とデータを結びつける話がありました。AI にデータを正しく使わせるには、データそのものだけでなく「そのデータが業務で何を意味するか」という文脈が要る。2日続けて、同じ問題意識に出会いました。

リアルタイム分析については、「レイテンシとスループットの両方が大事で、スループットの限界を超えるとシステムは崩れる」という話がありました。そのうえで、Lakehouse//RT は 12,000 QPS（1秒あたりのクエリ数）でもレイテンシを 100 ms 未満に保てる、と紹介されていました。Lakebase と Lakehouse//RT は、午後のセッションで詳しく聞きました。

## Lakebase と LTAP：アプリのデータベースを、分析の基盤の上に

午後最初のセッションは、この日いちばん楽しみにしていた Lakebase と LTAP の話です。

### Lakebase

Lakebase は、Databricks が提供する Postgres です。名前は Lake（データの保存）と Base（データベースのエンジン）を組み合わせたもので、Databricks が買収した Neon の技術をもとにしています。

ふつうの Postgres は、1台のサーバーがクエリの実行もデータの保存もこなします。Lakebase ではこれを分けていて、クエリを実行する Postgres はデータを手元に持ちません。データの変更履歴（WAL）は Safekeeper という複数台のサーバーが受け取って保存し、Pageserver がそれをデータのページに組み立て、最終的にクラウドのオブジェクトストレージに置きます。

保存と計算を分けたおかげで、次のようなことができます。

- 使っていないときは、計算資源をゼロまで縮められる
- データベースのコピー（ブランチ）を一瞬で作れる。開発やテスト用に本番のデータベースを丸ごと複製する、といった使い方ができる
- 過去の時点の状態に戻せる

### LTAP

あわせて紹介されたのが LTAP（Lake Transactional/Analytical Processing）です。

これまで、アプリのデータベースにあるデータを分析に使うには、CDC（変更データキャプチャ）で変更を取り出し、分析用の基盤へ運ぶパイプラインを作るのが一般的でした。ただ、パイプラインの運用、データが届くまでの遅れ、テーブルの構造が変わったときの追従など、手間のかかる部分が多くあります。

LTAP では、データを運びません。Pageserver がデータをオブジェクトストレージに書き出すときに、分析に向いた列指向の形式（Parquet）にも変換します。変換したデータは Delta や Iceberg のテーブルとして、分析のエンジンからそのまま読めます。講演によると、この変換は可逆で、Parquet から元の Postgres のデータを組み立て直すこともできるそうです。LTAP はまだ提供前（coming soon）とのことでした。

アプリのデータと分析のデータをどうつなぐかは、データ基盤でいつも悩みどころになる部分です。それを「運ぶ」のではなく「保存の段階で両方の形にする」という発想が面白く、講義で学んでいる行指向と列指向の違いが、こんな形で製品になるのかと感じました。

## Turing：自動運転 AI を支える MLOps 基盤

次は、完全自動運転を開発している Turing のセッションです。講演の内容は、Turing の技術ブログ「[Databricks の Declarative Automation Bundles を用いた機械学習データセット作成基盤の構築](https://zenn.dev/turing_motors/articles/46b5560dce0e3a)」とも重なっていたので、あわせて読んだ内容も交えて紹介します。

### データが性能を決める

従来の自動運転は、認識、予測、計画、制御の4つのモジュールに分かれ、高精度な地図とルールベースの判断に頼っていました。Turing は、カメラの映像から運転の判断までを1つのニューラルネットでつなぐ End-to-End のモデルを開発しています。さらにその先として、言語モデルを拡張したフィジカル基盤モデルを車に載せる方向も目指しているそうです。

このやり方では、モデルの性能がデータの量と質で決まります。歩行者、自転車、工事の作業員などが入り混じる日本の道路や、死角からの飛び出しのような見通しの悪い場面は、ただ走っているだけではなかなか集まりません。そこで、モデルの弱点から逆算して次に集めるデータを決め、そのシーンが出るように走行ルートまで計画しているそうです。モデルは1日に5〜10個作っているとのことでした。

### データセット作りを Databricks に移す

データ収集から車への搭載までの流れのうち、Databricks を使っているのは、集めた走行データを学習に使える形に整える部分です。

以前は、AWS のサービスを組み合わせて、動画から画像を切り出し、自動運転の公開データセット nuScenes と同じ形式のメタデータを作っていました。ブログによると、500時間分の走行データからデータセットを作るのに半日以上かかっていたそうです。画像を1枚ずつファイルにするので、ファイルの数が膨大になるという問題もありました。

新しい基盤では、次のように変えています。

- **動画のまま保存し、学習時にデコードする**：講演によると、画像に切り出すと容量が5〜10倍に増えていました。今は動画のまま保存し、学習のときに NVIDIA の GPU のデコーダで画像に戻しています。データセット作りは、メタデータを整えることに専念できるようになりました。
- **学習しやすい形式にする**：nuScenes の形式は、センサーやアノテーションごとにテーブルが分かれていて拡張しやすい反面、学習の1サンプルを組み立てるたびに多くのテーブルをたどる必要があります。新しい形式では1サンプルを1レコードにまとめ、MosaicML の Streaming Dataset（MDS）として出力しています。少ないファイル数で管理でき、学習時に速く読めます。
- **設定ファイルだけでデータセットを作る**：入力は、シーンの ID を並べた CSV と、パラメータをまとめた YAML の2つだけです。データセットの定義がファイルとして残るので、「どのモデルがどのデータで学習したか」もたどれます。

ブログによると、500時間分のデータセットは、条件にもよりますが60分以下で作れるようになったそうです。

### 開発の進め方の工夫

講演とブログで紹介されていた、開発の進め方の工夫も面白いものでした。

- **ジョブの定義もコードで管理する**：Declarative Automation Bundles（旧 Databricks Asset Bundles）を使い、ジョブの定義や実行環境を YAML でコードと一緒に管理しています。開発者ごとの開発環境、本番環境、統合テスト用の環境を切り替えられ、main にマージしなくても、開発中のブランチを本番と同じ Spark クラスタで試せます。本番へのデプロイは、Git のタグを打つと CI が行います。
- **正解のデータと比べてテストする**：統合テストでは、事前に作っておいた比較用のデータと、パイプラインの出力を比べます。テーブルの構造の変化や、依存パッケージの更新による問題も、ここで見つかったそうです。
- **処理を小さなステップに分ける**：処理は、共通の `PipelineStep` クラスを継承したステップとして書きます。どのテーブルを入力に使うかをステップごとに宣言し、新しい処理は新しいステップを足すだけで追加できます。講演では、こうした形にしておくとコーディングエージェントにも変更を任せやすい、という話もありました。

サーバーレスで動かすことの苦労話もありました。キャッシュの機能が使えないので途中結果をいったんテーブルに書き出す、依存パッケージのインストールに5分以上かかっていたのを事前にパッケージを用意して2分に縮める、失敗したときに自動でリトライされるのでデータセットの状態を管理して二重実行を防ぐ、といった具体的な工夫です。

自動運転というと、モデルそのものに目が行きがちです。ただ、このセッションで語られていたのは、データを集め、整え、何度でも学習を回せるようにする仕組みのほうでした。モデルを速く改善できるかどうかは、データ基盤の作りで決まるのだと実感しました。

## Lakehouse//RT：コピーせずにリアルタイム分析をする

最後に聞いたのは、Lakehouse//RT のセッションです。

### リアルタイム分析の3つの指標

講演では、リアルタイム分析で大事な指標として、次の3つが挙げられていました。

| 指標 | 意味 |
| --- | --- |
| データの鮮度 | データが生まれてから、クエリで見えるようになるまでの時間 |
| 応答時間 | 1つのクエリが返るまでの時間 |
| 同時実行性能 | 同時にさばけるクエリの数 |

### これまでのやり方の課題

ダッシュボードやアプリでリアルタイムに分析結果を見せたいとき、これまでは分析用のデータを ClickHouse のような別のシステムにコピーするのが一般的でした。講演では、この方法の課題として次の3つが挙げられていました。

1. **データの重複**：同じデータが2か所にあり、保存のコストがかかる
2. **ガバナンスの分断**：Unity Catalog の権限や来歴（リネージ）が、コピー先には効かない
3. **開発の遅れ**：別のシステムの運用や、コピーの仕組みの保守に手を取られる

Lakehouse//RT は、分析用のテーブル（Delta や Iceberg）をコピーせずにそのまま読み、ミリ秒単位で答えることで、これらを解こうとしています。独自の形式に変換しないのでロックインがなく、権限や来歴の管理も Unity Catalog のまま一貫させられます。

### 数字と位置づけ

講演では、次のような数字が紹介されていました。

- 最小のレイテンシは 10 ms
- 1秒あたり 12,000 クエリ
- 横長の1テーブルに集計クエリを流すベンチマーク ClickBench で 2.8 倍、複数のテーブルを結合するデータで約3倍の高速化

何と比べた数字なのかは講演では示されていなかったので、ベンダーの公称値として受け取っています。ClickHouse のようなリアルタイム分析用のデータベースは、テーブルの結合が苦手なことが多いので、結合ありでも速いという点は個人的に注目しています。

向いている用途も、はっきり説明されていました。

| 向いている | 向いていない |
| --- | --- |
| ミリ秒から数秒で終わる、同時にたくさん来る読み取り | 大量のデータを読み切る、長時間のスキャン |
| ダッシュボード、アプリの API、ユーザー向けの分析画面 | バッチ ETL、書き込みや変換 |

大量のデータを処理するバッチは従来のエンジンに任せ、Lakehouse//RT は短いクエリを大量にさばくことに専念する、という役割分担です。

## 楽天：AI がデータを書く時代のガバナンス

楽天の講演では、Iceberg を中心にしたデータ基盤と、AI のガバナンスの話がありました。

AI がデータを読むだけでなく書くようにもなり、ガバナンスを強める必要が高まっている、という問題意識です。課題として挙げられていたのは、次の4つが足りないことでした。

1. 誰が、どのモデルやエージェントを、どれだけ使っているかの可視化
2. エージェントが中で何をしたかを追える仕組み（オブザーバビリティ）
3. 危険な入出力を止めるガードレール
4. アクセス制御

その答えとして紹介されたのが Unity AI Gateway です。AI の利用コストの管理、リクエストの振り分け、利用状況の追跡、セキュリティとアクセス制御、AI 資産の登録簿といった機能を持ちます。データの資産（テーブルやファイル）は Unity Catalog で、AI の資産（モデル、エージェント、MCP サーバー、スキル）の実行は Unity AI Gateway で管理し、この2本柱で統合的なガバナンスを実現する、という構成でした。

前の日の Architecture Conference でも、AI エージェントに固有の ID と権限を与え、最小権限の原則を当てはめる話がありました。AI に仕事を任せるほど、「誰が、何を、どこまでしてよいか」を決める仕組みが大事になる。2日間を通して、そう感じました。

## おわりに

1日を通して印象に残ったのは、Databricks の製品の多くが同じ方針で作られていることです。

> データは1か所に置き、使い道ごとにエンジンを分ける。データを別のシステムへコピーしない。

アプリのデータベース（Lakebase）、バッチ処理、対話的な分析、リアルタイム分析（Lakehouse//RT）と、用途ごとにエンジンを用意し、どれも同じデータを読む。LTAP は「アプリのデータベースから分析へのコピー」を、Lakehouse//RT は「分析からリアルタイム提供へのコピー」をなくすための仕組みでした。

また、ストレージと計算の分離、行指向と列指向、正規化と非正規化、キャッシュといった、いま講義で学んでいる概念が、実際の製品や事例の中で次々に出てきたのも楽しい体験でした。製品の発表を聞きに行ったつもりが、データベースの授業の続きを聞いているような気分になる場面もありました。

それぞれの技術の中身については、別の記事でじっくり調べて書いてみるつもりです。
