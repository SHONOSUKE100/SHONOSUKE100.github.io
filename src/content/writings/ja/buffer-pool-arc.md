## ヒット率が 1% 違うと何が起きるか

データベースが速いかどうかは、多くの場合、欲しいデータがメモリにあったかどうかで決まる。

メモリからの読み出しは約 100 ナノ秒、SSD からは約 100 マイクロ秒。1000 倍の差がある。メモリにデータがあった割合を **ヒット率** と呼ぶと、1回の読み出しにかかる平均時間はおおよそ次の式になる。

```text
平均時間 = ヒット率 × 0.1µs ＋ (1 − ヒット率) × 100µs
```

ヒット率が 99% なら平均は約 1.1µs、98% なら約 2.1µs だ。たった 1% 下がっただけで、平均の読み出し時間はほぼ 2 倍になる。ミスしたときの 100µs が、それだけ重い。

だからデータベースは、限られたメモリに何を残し、何を追い出すかを工夫する。この記事では、その決め方（置換方式）のうち LRU、LFU、ARC の3つを自分で実装し、4種類のワークロードでヒット率を比べてみる。

先に結論を書いておく。

> どの追い出し方式が最適かは、ワークロード次第で変わる。ARC は「追い出して後悔したか」を手がかりに、その使い分けを自分で調整する。

## バッファプールとは

データベースは、ディスク上のデータを **ページ** という固定サイズの塊（PostgreSQL なら 8KB）で扱う。ディスクから読み込んだページは、メモリ上の決まった場所に置いておく。この場所が **バッファプール** だ。

![メモリ上のバッファプールとディスクの関係。クエリが page 2 を要求すると、page table を見て frame 1 にあることが分かる。なければディスクから空いているフレームに読み込む](/images/writings/buffer-pool-arc/buffer-pool.svg)

*図1：バッファプールの構成*

バッファプールは、ページを置く枠（**フレーム**）の配列と、どのページがどのフレームにあるかを記録した表（**page table**）でできている。クエリがページを要求すると、バッファプールはまず page table を見る。

- あれば **ヒット**。メモリ上のページをそのまま返す。
- なければ **ミス**。ディスクからページを読み込み、空いているフレームに置く。

フレームの数には限りがあるので、いずれ満杯になる。そのときは、どれか1つのページを追い出して場所を空ける。どのページを追い出すかの決め方が置換方式（replacement policy）で、この記事の主役である。PostgreSQL の `shared_buffers` や MySQL InnoDB の `innodb_buffer_pool_size` は、このバッファプールの大きさを決める設定だ。

実際のデータベースには、ほかにも「使用中のページは追い出さない（ピン）」「書き換えたページは、ディスクに書き戻してから追い出す（dirty）」といったルールがある。今回はヒット率だけを比べたいので、これらは扱わない。

## 実験のしかけ

ページ番号の並びを1つずつ受け取り、ヒットしたかどうかを数えるだけのシミュレーターを Python で作った。ディスクもスレッドも使わない。キャッシュの大きさは 100 ページ、普段使うページは 1000 種類で、各ワークロードに 10 万回アクセスする。

比べる基準として、**OPT**（Belady の最適方式）も測る。次に使われるのが一番先のページを追い出す方式で、未来のアクセスをすべて知っていないと実行できない。現実には作れないものの、これ以上のヒット率は出せないという上限として使える。

ワークロードは次の4つを用意した。

![4つのワークロードのアクセスの様子。横軸がアクセスの順番、縦軸がページ番号。W1 は人気ページに偏ったランダムアクセス、W2 は 150 ページを順に繰り返し読むのこぎり波、W3 は W1 に一度だけ読むスキャンのページが混ざったもの、W4 は途中で人気ページの集合がまるごと入れ替わるもの](/images/writings/buffer-pool-arc/workloads.svg)

*図2：4つのワークロードのアクセスの様子*

| # | 名前 | 中身 | 実務のイメージ |
| --- | --- | --- | --- |
| W1 | 偏りあり | 一部の人気ページにアクセスが集中する（Zipf 分布） | Web サービスの普段のトランザクション（OLTP） |
| W2 | ループスキャン | キャッシュより少し大きい 150 ページを、何周も順に読む | 同じテーブルを何度も読み直す結合処理 |
| W3 | 偏り＋全件スキャン | W1 と同時に、一度しか読まないページを順に読むバッチが流れる（アクセスの約 1/3） | 昼間の OLTP の裏で、分析用のバッチが走る |
| W4 | 人気の入れ替わり | 途中で、人気ページの集合がまるごと別のページに変わる | セールの開始やトレンドの変化 |

Zipf 分布は、人気が k 番目のページが 1/k に比例した確率で選ばれる分布で、ごく一部のページにアクセスが集中する。

W3 のスキャンで読むページは一度しか現れないので、どの方式でも必ずミスする。そこで W3 だけは、スキャン以外の普段のアクセスについてヒット率を測った。バッチが走っているあいだに、普段のアクセスのヒット率がどれだけ下がるかを見たいからだ。

## 定番の2つ：LRU と LFU

### LRU：最近使ったものは、またすぐ使う

LRU（Least Recently Used）は、一番昔に使われたページを追い出す。最近使われたページは、またすぐ使われるだろうという読みだ。

ページを使われた順に並べておけばよいので、Python の `OrderedDict` を使うと十数行で書ける。

```python
from collections import OrderedDict

class LRU:
    def __init__(self, capacity):
        self.capacity = capacity
        self.pages = OrderedDict()  # 先頭が一番古い、末尾が一番新しい

    def access(self, page):
        if page in self.pages:
            self.pages.move_to_end(page)  # ヒット：一番新しい位置へ
            return True
        if len(self.pages) >= self.capacity:
            self.pages.popitem(last=False)  # 満杯：一番古いページを追い出す
        self.pages[page] = None
        return False
```

アクセスのたびに並べ替えるのは重いので、実際のデータベースでは LRU を軽くした CLOCK がよく使われる。基本の CLOCK は、ページごとに「最近使われたか」の1ビットだけを持ち、時計の針のように順に見回って、ビットが立っていないページを追い出す。PostgreSQL の clock-sweep もその仲間だが、1ビットの代わりに小さな使用回数のカウンタ（usage_count）を持つ。針が通るたびにカウンタを1つ減らし、0 になっているページを追い出す。

### LFU：よく使われるものは、これからも使う

LFU（Least Frequently Used）は、使われた回数が一番少ないページを追い出す。人気のページはこれからも人気だろう、という読みである。今回の実装では、回数が同じならその中で一番昔に使われたページを追い出し、追い出したページの回数は忘れることにした。

### 第1ラウンドの結果

![LRU、LFU、OPT のヒット率の比較。W1 は LRU 58%、LFU 67%、OPT 75%。W2 は LRU と LFU が 0%、OPT 66%。W3 は LRU 48%、LFU 65%、OPT 75%。W4 は LRU 57%、LFU 34%、OPT 75%](/images/writings/buffer-pool-arc/round1.svg)

*図3：第1ラウンドのヒット率（LRU・LFU・OPT）*

人気ページの顔ぶれが変わらない W1 では、回数を数える LFU が 67% で、LRU の 58% を上回った。

差が大きく開いたのは W3 と W4 で、しかも負ける側が入れ替わる。

W3 でヒット率が大きく下がったのは LRU のほうだ。W1 では 58% だったのが、バッチのスキャンが混ざると 48% まで落ちた。スキャンで読んだページは二度と使われないのに、LRU はそれを最近使ったページとして残し、代わりに何度も使われる人気ページを追い出してしまう。この現象は sequential flooding と呼ばれる。LFU は使用回数が 1 のスキャンのページから先に捨てるので、65% を保った。

W4 では逆に、LFU が 34% まで下がった。前半の人気ページは使用回数が大きいまま残るので追い出されず、後半の新しい人気ページは、使用回数が 1 のうちに次の追い出しの対象になってしまう。LRU では、使われなくなった前半の人気ページが古い順に追い出されていくので、57% と W1 並みのヒット率が出た。

W2 はどちらも 0% だった。これは後の考察で扱う。

最近使ったかだけを見る LRU にも、何回使ったかだけを見る LFU にも、ヒット率が大きく下がる場面がある。両方の情報を、状況に応じて使い分けたい。それをするのが ARC だ。

## ARC：追い出して後悔したら学ぶキャッシュ

### アイデア

ARC（Adaptive Replacement Cache）は、IBM の Nimrod Megiddo と Dharmendra Modha が 2003 年に発表した置換方式だ。

アイデアは2つある。まず、キャッシュを「1回だけ使われたページの組」と「2回以上使われたページの組」に分ける。前者が LRU の得意な最近性を、後者が LFU の得意な頻度を受け持つ。そのうえで、2つの組にキャッシュを何ページずつ割り当てるかを、ワークロードに合わせて自動で動かす。

割り当てを動かす手がかりは、追い出したページがまた必要になったかどうかである。

### 4つのリスト

ARC は4つのリストを持つ。

![ARC の4つのリスト。左から B1、T1、T2、B2。T1 と T2 が実際にキャッシュにあるページで、合計は容量 c。B1 と B2 は追い出したページの ID だけを覚えるゴースト。T1 と T2 の境目は p で左右に動く](/images/writings/buffer-pool-arc/arc-lists.svg)

*図4：ARC の4つのリスト*

| リスト | 中身 |
| --- | --- |
| T1 | 1回だけ使われたページ（最近の組） |
| T2 | 2回以上使われたページ（常連の組） |
| B1 | T1 から追い出したページの ID だけ（ゴースト） |
| B2 | T2 から追い出したページの ID だけ（ゴースト） |

実際にキャッシュに入っているのは T1 と T2 のページで、合計がキャッシュの容量 c になる。B1 と B2 は **ゴーストリスト** と呼ばれる。ページの中身は持たず ID だけを覚えているので、メモリはほとんど使わない。

もう1つ、ARC は **p** という値を持つ。T1 に何ページ割り当てたいかを表す目標サイズで、T1 と T2 の境目にあたる。p が大きいほど最近の組を、小さいほど常連の組を重視する。

### ゴーストリストは「後悔センサー」

ARC の一番面白いところは、ゴーストリストの使い方だと思う。

アクセスされたページがキャッシュになく、B1 に ID が残っていたとする。最近の組から追い出したページが、すぐまた必要になったわけだ。最近の組を早く追い出しすぎた、という後悔である。そこで ARC は p を増やし、T1 の取り分を広げる。

B2 に ID が残っていたら、常連の組を早く追い出しすぎたことになる。今度は p を減らし、T2 の取り分を広げる。

p を動かす量は、反対側のゴーストリストとの大きさの比で決まる。B1 に当たったときは `max(|B2| / |B1|, 1)` だけ増やすので、小さいほうのゴーストに当たったときほど大きく動く。

つまりゴーストリストは、追い出した判断が間違っていたかを測り、その結果で次の判断を変えるための「後悔センサー」だ。

### アクセスしたときの4つのケース

ページ x にアクセスしたとき、ARC の動きは x がどこにあるかで4つに分かれる。

![ARC がページにアクセスしたときの4つのケースのフローチャート。T1 か T2 にあればヒットで T2 の先頭へ。B1 にあれば p を増やし、B2 にあれば p を減らし、1ページ追い出して T2 の先頭へ。どこにもなければ、満杯なら追い出して T1 の先頭へ](/images/writings/buffer-pool-arc/arc-flow.svg)

*図5：アクセスしたときの4つのケース*

1. T1 か T2 にある（ヒット）：T2 の先頭へ移す。2回目以上のアクセスなので、常連の組に入る。
2. B1 にある：p を増やし、1ページ追い出して場所を空けてから、x を T2 の先頭に入れる。
3. B2 にある：p を減らし、あとは2と同じ。
4. どこにもない：満杯なら1ページ追い出し、x を T1 の先頭に入れる。

追い出すときは、T1 の大きさが p より大きければ T1 の末尾から、そうでなければ T2 の末尾から追い出し、そのページの ID をそれぞれ B1 か B2 に移す。p は、次にどちらの組から追い出すかを決める基準になっている。

### 手で追ってみる

容量 3 のキャッシュに、`A B C A D B E A` の順でアクセスしてみる。各リストは左が先頭（新しい）、右が末尾（古い）。この表は、後で紹介する実装を実際に動かして作った。

| # | アクセス | 結果 | T1 | T2 | B1 | B2 | p |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 1 | A | 新規 | A | | | | 0 |
| 2 | B | 新規 | B A | | | | 0 |
| 3 | C | 新規 | C B A | | | | 0 |
| 4 | A | ヒット | C B | A | | | 0 |
| 5 | D | 新規 | D C | A | B | | 0 |
| 6 | B | B1 に当たる | D | B A | C | | 1 |
| 7 | E | 新規 | E D | B | C | A | 1 |
| 8 | A | B2 に当たる | E | A B | D C | | 0 |

4番目の A は T1 にあるのでヒットし、2回目なので T2 に移る。

最初に追い出しが起きるのは、キャッシュが満杯になったあとの D のときだ。T1 の大きさ（2）が p（0）より大きいので、T1 の末尾の B を追い出し、ID を B1 に残す。その直後にアクセスされた B は、B1 に残っていた。最近の組を追い出しすぎたので、p を 0 から 1 に増やす。場所を空けるために T1 の末尾の C を追い出し、B は2回目なので T2 に入れる。

E のときは、T1 の大きさ（1）が p（1）を超えていないので、追い出されるのは T2 の末尾の A になり、その ID が B2 に残る。最後にその A がアクセスされると、今度は常連を追い出しすぎたと分かり、p は 1 から 0 に戻る。

アクセスの傾向に合わせて、p が行ったり来たりしている。

### 実装

論文の手順をそのまま Python にすると、70 行ほどになる。各リストは `OrderedDict` で、先頭が古い側（追い出す側）、末尾が新しい側だ。

```python
from collections import OrderedDict

class ARC:
    def __init__(self, capacity):
        self.c = capacity
        self.p = 0.0  # T1 の目標サイズ
        self.t1, self.t2 = OrderedDict(), OrderedDict()
        self.b1, self.b2 = OrderedDict(), OrderedDict()

    def _replace(self, in_b2):
        # T1 が目標 p より大きければ T1 から、そうでなければ T2 から追い出し、ID をゴーストへ
        if self.t1 and ((in_b2 and len(self.t1) == self.p) or len(self.t1) > self.p):
            old, _ = self.t1.popitem(last=False)
            self.b1[old] = None
        else:
            old, _ = self.t2.popitem(last=False)
            self.b2[old] = None

    def access(self, x):
        # ケース1: キャッシュにある（ヒット）→ T2 の先頭へ
        if x in self.t1:
            del self.t1[x]
            self.t2[x] = None
            return True
        if x in self.t2:
            self.t2.move_to_end(x)
            return True

        # ケース2: B1 にある →「最近の組を追い出しすぎた」ので p を増やす
        if x in self.b1:
            self.p = min(self.c, self.p + max(len(self.b2) / len(self.b1), 1))
            self._replace(in_b2=False)
            del self.b1[x]
            self.t2[x] = None
            return False

        # ケース3: B2 にある →「常連を追い出しすぎた」ので p を減らす
        if x in self.b2:
            self.p = max(0.0, self.p - max(len(self.b1) / len(self.b2), 1))
            self._replace(in_b2=True)
            del self.b2[x]
            self.t2[x] = None
            return False

        # ケース4: どこにもない → T1 の先頭へ
        l1 = len(self.t1) + len(self.b1)
        total = l1 + len(self.t2) + len(self.b2)
        if l1 == self.c:
            if len(self.t1) < self.c:
                self.b1.popitem(last=False)
                self._replace(in_b2=False)
            else:
                self.t1.popitem(last=False)
        elif l1 < self.c and total >= self.c:
            if total == 2 * self.c:
                self.b2.popitem(last=False)
            self._replace(in_b2=False)
        self.t1[x] = None
        return False
```

ケース4の条件分岐は少し複雑に見える。これは、ゴーストリストが際限なく大きくならないようにするためのものだ。ARC は、T1 と B1 の合計を c 以下に、4つのリストの合計を 2c 以下に保つ。最近の組の履歴はキャッシュ1つ分まで、ゴーストを含めた全体はキャッシュ2つ分まで、ということだ。この約束を破りそうなときに、古いゴーストを先に捨てている。

実装がこの約束を守り続けているかは、10 万回のアクセスのあいだ毎回チェックするテストで確かめた。

## 第2ラウンド：ARC を加えて再実験

*図6：第2ラウンドのヒット率（ARC を追加）*

| ワークロード | LRU | LFU | ARC | OPT |

### p の動きを見る

ARC が実際にどう調整しているのかを、p の時間変化で見てみる。

![ARC の p の時間変化。細い線が実際の値、太い線が移動平均。W1 と W3 では p はほとんどの時間 10 未満にとどまる。W2 では 0 のまま動かない。W4 では人気が入れ替わった直後に p が跳ね上がり、その後また下がる](/images/writings/buffer-pool-arc/arc-p.svg)

*図7：ARC の p の時間変化*

W1 と W3 では、p はほとんどの時間 10 未満の小さな値にとどまる（中央値は W1 で 5、W3 で 2）。キャッシュ 100 ページのうち、おおむね 90 ページ以上を常連の組（T2）に割り当てているということだ。W3 のスキャンで読んだページは T1 に入り、二度と使われないまま T1 の末尾から追い出されていく。人気ページのいる T2 からはほとんど追い出されないので、LRU のような sequential flooding が起きない。

W4 で人気が入れ替わった直後には、p が跳ね上がる。p が小さいので、T1 に入った新しい人気ページは、次の追い出しですぐ T1 の末尾から追い出される。ところが、人気ページなのですぐにまたアクセスされ、B1 で何度も見つかる。ARC はこれを最近の組を追い出しすぎたと判断して、T1 の取り分を一時的に広げる。新しい人気ページが T2 に移り終わると、p はまた下がる。LFU が古い使用回数のせいでヒット率を落とした場面で、ARC は B1 に当たった回数をもとに、取り分を切り替えたわけだ。

「後悔から学ぶ」と書いたのは、この動きのことである。

## 考察

### ARC でも勝てない場面：ループスキャン

W2 では、LRU、LFU、ARC の全員が 0% だった。キャッシュ（100 ページ）より少しだけ大きい範囲（150 ページ）を順に繰り返し読むと、どのページも、次に使われる直前に追い出されてしまう。

ARC が学べない理由は、先ほどの約束にある。W2 ではどのページも1回ずつしか現れないように見えるので、T1 がキャッシュ全体を占める。すると、T1 と B1 の合計を c 以下に保つ約束のために、B1 には何も残せない。後悔センサーが空なので、p は 0 のまま動かない。

一方、OPT は 66% を出している。このパターンでは、最近使ったものほど追い出す（MRU）のが正解だ。ループの一部をずっとキャッシュに残しておけば、そこだけは毎周ヒットする。

実際のデータベースは、この問題を置換方式とは別の仕組みで解決している。PostgreSQL は大きなテーブルをスキャンするとき、そのスキャンに小さなリングバッファだけを使わせて、スキャンで読んだページがバッファプール全体を埋めないようにしている。スキャンで読んだページをバッファプールに入れず、そのクエリの手元だけで使う方法（バイパス）もある。データベースはクエリの実行計画を知っているので、これからこのテーブルを何周も読むと分かれば、そのスキャンにだけ別の追い出し方を使うこともできる。

万能の置換方式はない。ARC の強みは、多くの場面で大負けしないことにある。

### コストと、実際のデータベースでの採用

ARC にもコストはある。ゴーストリストの分だけ管理する情報が増え、最大でキャッシュ容量の2倍のページ ID を持つ。また、アクセスのたびにリストを並べ替えるので、多くのスレッドが同時にアクセスすると、リストを守るロックの取り合いになりやすい。CLOCK のような軽い方式が好まれるのは、これも理由の1つだ。

実際の採用例を見ると、ZFS（ファイルシステム）は、ARC を改良したものをキャッシュに使っている。PostgreSQL は 8.0 で一度 ARC を採用したが、IBM が出願していた ARC の特許を避けるため、8.0.2 で 2Q という別の方式に置き換えた。8.1 以降は clock-sweep を使っている。MySQL InnoDB は、LRU のリストを old と young の2つに分ける。新しいページはまず old に入り、もう一度使われたときに young に移る。ただし、最初のアクセスから一定時間（初期値は 1 秒）たつまでは、使われても young に移らない。そのため、スキャンで読んだページは young に入りにくく、sequential flooding が起きにくい。ARC の T1 と T2 に近い考え方だ。

余談になるが、「固定サイズの枠に区切り、表で居場所を管理し、足りなくなったら選んで追い出す」という設計は、データベースの外にもある。LLM の推論エンジン vLLM の PagedAttention は、GPU メモリを固定サイズのブロックに区切り、ブロックテーブルで管理する。分野は違っても、キャッシュを設計するときにぶつかる問題は同じだ。

## まとめ

LRU は全件スキャンが混ざるとヒット率が落ち、LFU は人気が入れ替わるとヒット率が落ちた。ARC はゴーストリストで追い出しの判断が間違っていたかを測り、2つの組の取り分を自分で調整することで、どちらの場面でも大負けしなかった。ただ、キャッシュより少し大きい範囲を繰り返し読むループスキャンには、ARC も勝てない。

どの追い出し方式が最適かは、ワークロード次第で変わる。ARC の面白さは、その調整を、キャッシュが自分の後悔から学んで行うところにある。

実験のコードは [GitHub](https://github.com/SHONOSUKE100/SHONOSUKE100.github.io/tree/main/experiments/buffer-pool-replacement) に置いている。乱数の種を固定しているので、同じ結果を再現できる。
