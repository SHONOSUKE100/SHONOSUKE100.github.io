## ヒット率が 1% 違うと何が起きるか

データベースが速いかどうかは、多くの場合「欲しいデータがメモリにあったかどうか」で決まる。

メモリからの読み出しは約 100 ナノ秒、SSD からの読み出しは約 100 マイクロ秒かかる。その差は 1000 倍だ。メモリにデータがあった割合を **ヒット率** と呼ぶと、1回の読み出しにかかる平均時間はおおよそ次の式で表せる。

```text
平均時間 = ヒット率 × 0.1µs ＋ (1 − ヒット率) × 100µs
```

ヒット率が 99% なら平均は約 1.1µs、98% なら約 2.1µs になる。**ヒット率がたった 1% 下がるだけで、平均の読み出し時間はほぼ 2 倍になる。** ミスしたときの 100µs が、それだけ重いということだ。

だからデータベースは、限られたメモリに「何を残し、何を追い出すか」に本気で取り組む。この記事では、その決め方（置換方式）のうち代表的な LRU、LFU、そして ARC を自分で実装し、4種類のワークロードでヒット率を比べてみる。

先に結論を書いておく。

> どの追い出し方式が最適かは、ワークロード次第で変わる。ARC は「追い出して後悔したか」を手がかりに、その使い分けを自分で調整する。

## バッファプールとは

データベースは、ディスク上のデータを **ページ** という固定サイズの塊（PostgreSQL なら 8KB）で扱う。そして、ディスクから読み込んだページをメモリ上に置いておく場所を持っている。これが **バッファプール** だ。

![メモリ上のバッファプールとディスクの関係。クエリが page 2 を要求すると、page table を見て frame 1 にあることが分かる。なければディスクから空いているフレームに読み込む](/images/writings/buffer-pool-arc/buffer-pool.svg)

バッファプールは、ページを置く枠（**フレーム**）の配列と、「どのページがどのフレームにあるか」を記録した表（**page table**）でできている。クエリがページを要求すると、バッファプールはまず page table を見る。

- あれば **ヒット**。メモリ上のページをそのまま返す。
- なければ **ミス**。ディスクからページを読み込み、空いているフレームに置く。

フレームの数には限りがあるので、いずれ満杯になる。そのときは、どれか1つのページを追い出して場所を空ける必要がある。**どのページを追い出すかの決め方** が置換方式（replacement policy）で、この記事の主役だ。

PostgreSQL の `shared_buffers` や MySQL InnoDB の `innodb_buffer_pool_size` は、このバッファプールの大きさを決める設定である。

実際のデータベースでは、ほかにも「使用中のページは追い出さない（ピン）」「書き換えたページは、ディスクに書き戻してから追い出す（dirty）」といったルールがある。今回はヒット率だけを比べたいので、これらは扱わない。

## 実験のしかけ

ページ番号の並びを1つずつ渡し、ヒットしたかどうかを数えるだけの小さなシミュレーターを Python で作った。ディスクもスレッドも使わない。条件は次のとおりだ。

- キャッシュの大きさは 100 ページ
- 普段使うページは 1000 種類
- 各ワークロードで 10 万回アクセスする

物差しとして、**OPT**（Belady の最適方式）も一緒に測る。OPT は「次に使われるのが一番先のページ」を追い出す方式で、未来のアクセスをすべて知っていないと実行できない。現実には作れないが、どれだけ頑張ってもこれ以上のヒット率は出せないという上限として使える。

ワークロードは4つ用意した。

![4つのワークロードのアクセスの様子。横軸がアクセスの順番、縦軸がページ番号。W1 は人気ページに偏ったランダムアクセス、W2 は 150 ページを順に繰り返し読むのこぎり波、W3 は W1 に一度だけ読むスキャンのページが混ざったもの、W4 は途中で人気ページの集合がまるごと入れ替わるもの](/images/writings/buffer-pool-arc/workloads.svg)

| # | 名前 | 中身 | 実務のイメージ |
| --- | --- | --- | --- |
| W1 | 偏りあり | 一部の人気ページにアクセスが集中する（Zipf 分布） | Web サービスの普段のトランザクション（OLTP） |
| W2 | ループスキャン | キャッシュより少し大きい 150 ページを、何周も順に読む | 同じテーブルを何度も読み直す結合処理 |
| W3 | 偏り＋全件スキャン | W1 と同時に、一度しか読まないページを順に読むバッチが流れる（アクセスの約 1/3） | 昼間の OLTP の裏で、分析用のバッチが走る |
| W4 | 人気の入れ替わり | 途中で、人気ページの集合がまるごと別のページに変わる | セールの開始やトレンドの変化 |

W3 のスキャンで読むページは一度しか現れないので、どの方式でも必ずミスする。そこで W3 だけは、スキャン以外の普段のアクセスに対するヒット率を測った。バッチが走っているせいで、普段のアクセスがどれだけ巻き添えを食うかを見たいからだ。

## 定番の2つ：LRU と LFU

### LRU：最近使ったものは、またすぐ使う

**LRU**（Least Recently Used）は、**一番昔に使われたページ** を追い出す。最近使われたページは、またすぐ使われるだろうという読みだ。

実装は、ページを使われた順に並べておくだけでよい。Python の `OrderedDict` を使えば、次の十数行で書ける。

```python
from collections import OrderedDict

class LRU:
    def __init__(self, capacity):
        self.capacity = capacity
        self.pages = OrderedDict()  # 先頭が一番古い、末尾が一番新しい

    def access(self, page):
        if page in self.pages:
            self.pages.move_to_end(page)  # ヒット：一番新しい位置へ
            return True
        if len(self.pages) >= self.capacity:
            self.pages.popitem(last=False)  # 満杯：一番古いページを追い出す
        self.pages[page] = None
        return False
```

実際のデータベースでは、アクセスのたびに並べ替えるのが重いので、LRU を軽くした **CLOCK** がよく使われる。PostgreSQL の clock-sweep もその仲間だ。ページごとに「最近使われたか」の1ビットだけを持ち、時計の針のように順に見回って、ビットが立っていないページを追い出す。

### LFU：よく使われるものは、これからも使う

**LFU**（Least Frequently Used）は、**使われた回数が一番少ないページ** を追い出す。人気のページは、これからも人気だろうという読みだ。回数が同じなら、その中で一番昔に使われたページを追い出すことにした。また今回は、追い出したページの回数は忘れる方式にしている。

### 第1ラウンドの結果

![LRU、LFU、OPT のヒット率の比較。W1 は LRU 58%、LFU 67%、OPT 75%。W2 は LRU と LFU が 0%、OPT 66%。W3 は LRU 48%、LFU 65%、OPT 75%。W4 は LRU 57%、LFU 34%、OPT 75%](/images/writings/buffer-pool-arc/round1.svg)

結果を見ると、どちらにも得意な場面と苦手な場面がある。

**W1（偏りあり）では LFU が勝つ。** 人気ページの顔ぶれが変わらないので、回数を数える LFU の読みがそのまま当たる。

**W3（偏り＋全件スキャン）では、LRU だけが大きく落ちる。** W1 では 58% だったのに、バッチのスキャンが混ざると 48% になった。スキャンで読んだページは二度と使われないのに、LRU はそれを「最近使ったページ」として大事にとっておき、代わりに何度も使われる人気ページを追い出してしまう。この現象は **sequential flooding** と呼ばれる。LFU は、使用回数が 1 のスキャンのページから先に捨てるので、ほとんど影響を受けない（65%）。

**W4（人気の入れ替わり）では、今度は LFU が崩れる（34%）。** 前半の人気ページが大きな使用回数を抱えたままキャッシュに居座り、後半の新しい人気ページは、入ってきてもすぐ追い出されてしまう。LRU は、古いページが自然に押し出されるので影響を受けない（57%）。

**W2（ループスキャン）では、どちらも 0% だった。** これは後の考察で扱う。

つまり、「最近使ったか」だけを見る LRU も、「何回使ったか」だけを見る LFU も、それぞれ苦手な場面がある。両方の情報を、状況に応じて使い分けたい。それを実現するのが ARC だ。

## ARC：追い出して後悔したら学ぶキャッシュ

### アイデア

**ARC**（Adaptive Replacement Cache）は、IBM の Nimrod Megiddo と Dharmendra Modha が 2003 年に発表した置換方式だ。

アイデアは2つある。

1. キャッシュを「1回だけ使われたページの組」と「2回以上使われたページの組」に分ける。前者が LRU の得意な「最近」、後者が LFU の得意な「頻度」を担当する。
2. 2つの組にキャッシュを何ページずつ割り当てるかを、ワークロードに合わせて自動で動かす。

割り当てを動かす手がかりになるのが、「追い出したページが、また必要になったか」という情報だ。

### 4つのリスト

ARC は4つのリストを持つ。

![ARC の4つのリスト。左から B1、T1、T2、B2。T1 と T2 が実際にキャッシュにあるページで、合計は容量 c。B1 と B2 は追い出したページの ID だけを覚えるゴースト。T1 と T2 の境目は p で左右に動く](/images/writings/buffer-pool-arc/arc-lists.svg)

| リスト | 中身 |
| --- | --- |
| T1 | 1回だけ使われたページ（最近の組） |
| T2 | 2回以上使われたページ（常連の組） |
| B1 | T1 から追い出したページの **ID だけ**（ゴースト） |
| B2 | T2 から追い出したページの **ID だけ**（ゴースト） |

実際にキャッシュに入っているのは T1 と T2 のページで、合計がキャッシュの容量 c になる。B1 と B2 は **ゴーストリスト** と呼ばれ、ページの中身は持たず、ID だけを覚えている。だからメモリはほとんど使わない。

そして ARC は、**p** という値を持つ。p は「T1 に何ページ割り当てたいか」という目標サイズで、T1 と T2 の境目にあたる。p が大きいほど最近の組を、小さいほど常連の組を重視することになる。

### ゴーストリストは「後悔センサー」

ARC の一番面白いところは、ゴーストリストの使い方だ。

アクセスされたページがキャッシュになく、B1 に ID が残っていたとする。これは「最近の組から追い出したページが、すぐまた必要になった」ということだ。つまり、**最近の組を早く追い出しすぎた** という後悔である。そこで ARC は p を増やし、T1 の取り分を広げる。

逆に B2 に ID が残っていたら、**常連の組を早く追い出しすぎた** という後悔だ。今度は p を減らし、T2 の取り分を広げる。

p を動かす量は、反対側のゴーストリストとの大きさの比で決まる。B1 に当たったときは `max(|B2| / |B1|, 1)` だけ p を増やす。小さい方のゴーストに当たったときほど、大きく動く。

ゴーストリストは、ARC にとっての「後悔センサー」だ。追い出した判断が間違っていたかどうかを測り、その結果で次の判断を変える。

### アクセスしたときの4つのケース

ページ x にアクセスしたとき、ARC は x がどこにあるかで4つのケースに分かれる。

![ARC がページにアクセスしたときの4つのケースのフローチャート。T1 か T2 にあればヒットで T2 の先頭へ。B1 にあれば p を増やし、B2 にあれば p を減らし、1ページ追い出して T2 の先頭へ。どこにもなければ、満杯なら追い出して T1 の先頭へ](/images/writings/buffer-pool-arc/arc-flow.svg)

1. **T1 か T2 にある（ヒット）**：T2 の先頭へ移す。2回目以上のアクセスなので、常連の組に入る。
2. **B1 にある**：p を増やす。1ページ追い出して場所を空け、x を T2 の先頭に入れる。
3. **B2 にある**：p を減らす。1ページ追い出して場所を空け、x を T2 の先頭に入れる。
4. **どこにもない**：満杯なら1ページ追い出し、x を T1 の先頭に入れる。

追い出すときは、T1 の大きさが p より大きければ T1 の末尾から、そうでなければ T2 の末尾から追い出す。追い出したページの ID は、それぞれ B1 か B2 に移す。つまり p は「次にどちらの組から追い出すか」を決める基準になっている。

### 手で追ってみる

容量 3 のキャッシュに、`A B C A D B E A` の順でアクセスしてみる。各リストは、左が先頭（新しい）、右が末尾（古い）だ。この表は、後で紹介する実装を実際に動かして作った。

| # | アクセス | 結果 | T1 | T2 | B1 | B2 | p |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 1 | A | 新規 | A | | | | 0 |
| 2 | B | 新規 | B A | | | | 0 |
| 3 | C | 新規 | C B A | | | | 0 |
| 4 | A | **ヒット** | C B | A | | | 0 |
| 5 | D | 新規 | D C | A | B | | 0 |
| 6 | B | **B1 に当たる** | D | B A | C | | **1** |
| 7 | E | 新規 | E D | B | C | A | 1 |
| 8 | A | **B2 に当たる** | E | A B | D C | | **0** |

- **4**：A は T1 にあるのでヒット。2回目なので T2 に移る。
- **5**：D は初めてなのに、キャッシュは満杯だ。T1 の大きさ（2）が p（0）より大きいので、T1 の末尾 B を追い出し、ID を B1 に残す。
- **6**：B は B1 に残っていた。「最近の組を追い出しすぎた」ので p を 0 から 1 に増やす。場所を空けるため T1 の末尾 C を追い出し、B は2回目なので T2 に入る。
- **7**：E は初めて。今度は T1 の大きさ（1）が p（1）より大きくないので、T2 の末尾 A を追い出して B2 に残す。
- **8**：A は B2 に残っていた。「常連を追い出しすぎた」ので p を 1 から 0 に戻す。

アクセスの傾向に合わせて、p が行ったり来たりする様子が分かる。

### 実装

論文の手順をそのまま Python にすると、70 行ほどになる。各リストは `OrderedDict` で、先頭が古い側（追い出す側）、末尾が新しい側だ。

```python
from collections import OrderedDict

class ARC:
    def __init__(self, capacity):
        self.c = capacity
        self.p = 0.0  # T1 の目標サイズ
        self.t1, self.t2 = OrderedDict(), OrderedDict()
        self.b1, self.b2 = OrderedDict(), OrderedDict()

    def _replace(self, in_b2):
        # T1 が目標 p より大きければ T1 から、そうでなければ T2 から追い出し、ID をゴーストへ
        if self.t1 and ((in_b2 and len(self.t1) == self.p) or len(self.t1) > self.p):
            old, _ = self.t1.popitem(last=False)
            self.b1[old] = None
        else:
            old, _ = self.t2.popitem(last=False)
            self.b2[old] = None

    def access(self, x):
        # ケース1: キャッシュにある（ヒット）→ T2 の先頭へ
        if x in self.t1:
            del self.t1[x]
            self.t2[x] = None
            return True
        if x in self.t2:
            self.t2.move_to_end(x)
            return True

        # ケース2: B1 にある →「最近の組を追い出しすぎた」ので p を増やす
        if x in self.b1:
            self.p = min(self.c, self.p + max(len(self.b2) / len(self.b1), 1))
            self._replace(in_b2=False)
            del self.b1[x]
            self.t2[x] = None
            return False

        # ケース3: B2 にある →「常連を追い出しすぎた」ので p を減らす
        if x in self.b2:
            self.p = max(0.0, self.p - max(len(self.b1) / len(self.b2), 1))
            self._replace(in_b2=True)
            del self.b2[x]
            self.t2[x] = None
            return False

        # ケース4: どこにもない → T1 の先頭へ
        l1 = len(self.t1) + len(self.b1)
        total = l1 + len(self.t2) + len(self.b2)
        if l1 == self.c:
            if len(self.t1) < self.c:
                self.b1.popitem(last=False)
                self._replace(in_b2=False)
            else:
                self.t1.popitem(last=False)
        elif l1 < self.c and total >= self.c:
            if total == 2 * self.c:
                self.b2.popitem(last=False)
            self._replace(in_b2=False)
        self.t1[x] = None
        return False
```

ケース4の条件分岐が少し複雑に見えるが、これはゴーストリストが際限なく大きくならないようにするためのものだ。ARC は常に次の2つを守る。

- T1 と B1 の合計は c 以下（最近の組の履歴は、キャッシュ1つ分まで）
- 4つのリストの合計は 2c 以下（ゴーストを含めて、キャッシュ2つ分まで）

この約束を破りそうなときに、古いゴーストを先に捨てている。実装が約束を守り続けているかは、10 万回のアクセスのあいだ毎回チェックするテストで確かめた。

## 第2ラウンド：ARC を加えて再実験

![LRU、LFU、ARC、OPT のヒット率の比較。ARC は W1 で 64%、W2 で 0%、W3 で 66%、W4 で 64%](/images/writings/buffer-pool-arc/round2.svg)

| ワークロード | LRU | LFU | ARC | OPT |
| --- | ---: | ---: | ---: | ---: |
| W1 偏りあり | 57.7% | **66.6%** | 64.1% | 75.5% |
| W2 ループスキャン | 0.0% | 0.0% | 0.0% | 66.3% |
| W3 偏り+全件スキャン | 48.1% | 64.9% | **65.7%** | 75.4% |
| W4 人気の入れ替わり | 57.5% | 34.0% | **63.9%** | 75.4% |

ARC は、W1 では LFU に少し負けるものの、W3 と W4 では LRU と LFU のどちらよりも高い。LRU が崩れた W3 でも、LFU が崩れた W4 でも、ARC は崩れていない。**どのワークロードでも大負けしない** のが ARC の強みだ。

### p の動きを見る

ARC が実際にどう調整しているのかを、p の時間変化で見てみる。

![ARC の p の時間変化。細い線が実際の値、太い線が移動平均。W1 と W3 では p は 10 未満で落ち着いている。W2 では 0 のまま動かない。W4 では人気が入れ替わった直後に p が跳ね上がり、その後また下がる](/images/writings/buffer-pool-arc/arc-p.svg)

**W1 と W3 では、p は 10 未満の小さな値で落ち着いている。** キャッシュ 100 ページのうち 90 ページ以上を常連の組（T2）に割り当てているということだ。W3 のスキャンで読んだページは T1 に入り、二度と使われないまま T1 の末尾から追い出されていく。人気ページがいる T2 は荒らされない。LRU が sequential flooding で崩れた場面を、ARC はこうして切り抜けている。

**W4 では、人気が入れ替わった直後に p が跳ね上がる。** 新しい人気ページは、最初は T1 に入るが、まだ大きな T2 に押されてすぐ追い出される。ところがすぐにまたアクセスされるので、B1 で何度も見つかる。ARC はこれを「最近の組を追い出しすぎた」と判断して、T1 の取り分を一時的に広げる。新しい人気ページが T2 に定着すると、p はまた下がる。LFU が古い使用回数に縛られて崩れた場面で、ARC は自分の判断の誤りに気づき、素早く切り替えている。

これが「後悔から学ぶ」の実際の姿だ。

## 考察

### ARC でも勝てない場面：ループスキャン

W2 では、LRU、LFU、ARC の全員が 0% だった。キャッシュ（100 ページ）より少しだけ大きい範囲（150 ページ）を順に繰り返し読むと、どのページも「次に使われる直前」に追い出されてしまう。

ARC が学べない理由は、先ほどの約束にある。W2 ではすべてのページが1回ずつしか現れないように見えるので、T1 がキャッシュ全体を占める。すると「T1 と B1 の合計は c 以下」の約束により、B1 には何も残せない。後悔センサーが空っぽなので、p は 0 のまま動かない。

一方、OPT は 66% を出している。このパターンでの理想は「最近使ったものほど追い出す」（MRU）ことで、ループの一部をずっとキャッシュに残しておけば、そこだけは毎周ヒットする。

実際のデータベースは、この問題を置換方式とは別の仕組みで解決している。

- PostgreSQL は、大きなテーブルをスキャンするとき、小さなリングバッファだけを使わせる。スキャンがバッファプール全体を荒らさないようにするためだ。
- スキャンで読んだページをバッファプールに入れず、そのクエリの手元だけで使う方法（バイパス）もある。
- データベースはクエリの実行計画を知っているので、「これからこのテーブルを何周も読む」と分かれば、それに合った扱いができる。

万能の置換方式はない。ARC は「多くの場面で大負けしない」方式であって、どんな場面でも最適な方式ではない。

### コストと、実際のデータベースでの採用

ARC にもコストがある。

- ゴーストリストの分だけ、管理する情報が増える（最大でキャッシュ容量の2倍のページ ID）。
- アクセスのたびにリストを並べ替えるので、多くのスレッドが同時にアクセスすると、リストを守るロックの取り合いになりやすい。CLOCK のような軽い方式が好まれる理由の1つだ。

実際の採用例も見ておく。

- **ZFS**（ファイルシステム）は、ARC をキャッシュの中心に据えている。
- **PostgreSQL** は、8.0 で一度 ARC を採用した。しかし IBM の特許の問題があり、すぐに外して 8.0.2 で 2Q という方式に置き換え、8.1 以降は clock-sweep を使っている。
- **MySQL InnoDB** は、LRU のリストを old と young の2つに分ける方式を使う。新しいページはまず old に入り、もう一度使われたら young に移る。ARC の T1 と T2 に近い考え方で、スキャンへの強さを確保している。

余談になるが、この「固定サイズの枠に区切り、表で居場所を管理し、足りなくなったら賢く追い出す」という設計は、データベースの外にもある。たとえば LLM の推論エンジン vLLM の PagedAttention は、GPU メモリを固定サイズのブロックに区切り、ブロックテーブルで管理する。キャッシュの設計は、分野を越えて同じ問題を解いている。

## まとめ

- キャッシュのヒット率が 1% 下がるだけで、平均の読み出し時間はほぼ 2 倍になりうる。だからデータベースは「何を追い出すか」を工夫する。
- LRU は全件スキャンが混ざると崩れ（sequential flooding）、LFU は人気が入れ替わると崩れる。どちらにも苦手な場面がある。
- ARC は「最近の組」と「常連の組」に分け、ゴーストリストで「追い出して後悔したか」を測って、2つの取り分を自動で調整する。実験では、どのワークロードでも大負けしなかった。
- それでも、キャッシュより少し大きい範囲を繰り返し読むループスキャンには、ARC も勝てない。実際のデータベースは、リングバッファやバイパスといった別の仕組みも組み合わせている。

どの追い出し方式が最適かは、ワークロード次第で変わる。ARC の面白さは、その「ワークロード次第」を人が決めるのではなく、キャッシュ自身が後悔から学んで決めるところにある。

実験のコードは [GitHub](https://github.com/SHONOSUKE100/SHONOSUKE100.github.io/tree/main/experiments/buffer-pool-replacement) に置いている。乱数の種を固定しているので、同じ結果を再現できる。
