11月26日、Findy が羽田空港で開催した [Architecture Conference 2026](https://architecture-con.findy-tools.io/2026) に参加しました。

このカンファレンスに参加するのは2回目です。昨年参加したことがきっかけで、ソフトウェアアーキテクチャに興味を持ちました。同時に、アーキテクチャの難しさと、技術とビジネスドメインの両方で学ぶべきことがまだ多いことも痛感しました。

1年たった今年は、議論の中身をずっと深く理解できるようになっていました。この1年、職場のオンボーディング、Java の学習、『Clean Architecture』やデザインパターンの本を通して、ソフトウェアアーキテクチャを学ぶ機会がありました。

一方で、AI の急速な進歩によって、ソフトウェアの設計や開発の進め方を考え直すようにもなりました。

昨年のカンファレンスで聞いた、今も心に残っている言葉が2つあります。

- 「Garbage in, garbage out（ゴミを入れれば、ゴミが出てくる）」
- 「AI は加速装置である」

これまで人が多くの労力をかけていた作業を、AI がこなせるようになってきています。

こうした時代には、人と AI の両方とうまく意思疎通すること、暗黙知を明文化すること、曖昧さを減らすこと、明確な契約（インターフェース）を決めること、設計の判断を記録に残すことが、ますます大切になると考えています。

最終的に目指すのは、長く保守でき、変化に適応できるシステムをつくることです。

この記事では、参加したセッションで得た学びと、そこから考えたことをまとめます。

## 設計原則を問い直す：変えるべきもの、変えてはいけないもの

**Martin Fowler（Thoughtworks）、Kazutoshi Ono（クレディセゾン）**

基調講演では、デザインパターン、リファクタリング、エクストリームプログラミング（XP）といった設計原則の成り立ちをたどり、AI 時代にそれらがどんな意味を持つのかが議論されました。

### 学びと考えたこと

- Martin Fowler のウェブサイトという、貴重な学習リソースを知りました。
- デザインパターンは、オブジェクト指向のような複雑な考え方を理解し、使いこなす助けになります。初期のソフトウェアのデザインパターンが、Christopher Alexander のパタン・ランゲージに着想を得て、Smalltalk のユーザーインターフェース設計に応用されたものだと知り、興味を持ちました。
- オブジェクト指向の歴史で重要な役割を果たしたプログラミング言語、Smalltalk について知りました。
- XP は、プロジェクト管理と、自動テストや継続的インテグレーションといった技術的なプラクティスを一体にしたものです。同じように AI も、コードの書き方だけでなく、ソフトウェア開発の進め方そのものを変えつつあります。
- 特に面白いと感じたのが、エキスパート・ジェネラリストという考え方です。深い技術的知識に加えて、好奇心、分野をまたいで学ぶ力、協働する力、顧客のニーズへの関心をあわせ持つ人のことを指します。

AI 時代には、狭い分野の高い技術力だけでは、価値を生み出すのに十分でなくなるかもしれない、と私は受け取りました。問題をさまざまな視点から捉え、異なる専門を持つ人と協働する力が、ますます重要になっています。

## 本番運用できる AI エージェントのためのアーキテクチャ設計

**Keisuke Tsukagoshi（Google Cloud）**

AI エージェントを本番で運用するときの4つの課題が取り上げられました。品質と評価、責務と境界、セキュリティと権限、コストとレイテンシです。

### 学びと考えたこと

- 特に面白かったのは、社内の業務を AI に任せようとすると、組織が暗黙知や判断基準を明文化せざるを得なくなる、という点です。AI は単に作業を自動化するだけでなく、業務の属人化を減らす助けにもなります。
- プログレッシブ・ディスクロージャー（段階的な開示）という方法を知りました。エージェントには最初に概要だけを渡し、詳しい指示や知識は必要になったときに読ませる方法で、コンテキストウィンドウを効率よく使えます。
- エージェント・アイデンティティという考え方も興味深く感じました。エージェントごとに固有の ID と権限を与えれば、最小権限の原則のような従来のアクセス制御の考え方を、AI エージェントにもそのまま当てはめられます。
- AI エージェントには、明確なインターフェースとデータ契約が欠かせません。エージェント同士の通信には A2A、エージェントと外部のツールやリソースの接続には MCP が使えます。入出力を構造化すれば、これらの間の曖昧さを減らせます。
- セキュリティ上の制約や、結果が一意に決まるべき業務ルールは、プロンプトだけに頼らず、LLM の外側で強制すべきです。
- 人による承認は、すべての操作を一つずつ確認する形から、評価基準を決めて例外にだけ対応する形へと、少しずつ移っていけます。

一番の学びは、AI エージェントの導入が既存の業務の自動化にとどまらない、ということです。組織の中で知識、責務、権限、判断がどう組み立てられているかを見直し、形にする機会でもあります。

## AWS AI-DLC v2 に学ぶ、AI のためのドメイン境界の設計

**Junichi Kato（IDEO PLUS）**

AI が生成したコードにドメインの境界やアーキテクチャの原則を守らせるには、どうすればよいか。ドメイン知識、設計上の制約、検証を AI 駆動開発のワークフローに組み込む方法が紹介されました。

### 学びと考えたこと

- 機能テストに通ったからといって、その実装がアーキテクチャの原則やドメインの境界を守っているとは限りません。
- ドメインプリミティブや型システムを使えば、ドキュメントやプロンプトだけに頼らず、業務ルールや制約をコードの上で明示できます。
- AI-DLC に、ドメイン固有の設計ルール、センサーと呼ばれる自動検証の仕組み、承認ゲートを加えて、アーキテクチャ違反を検出する方法を知りました。
- AI-DLC は、アーキテクチャの知識や設計ルールを開発のワークフローに取り込み続けるための、フィードバックループになります。
- 既存のコードから仕様を抽出し、システムの再設計やモダナイゼーションの土台にする Reverse Spec Flow という方法を知りました。
- 実装の前に仕様の矛盾を見つける手段として、形式手法の可能性にも触れられていました。無駄な手戻りや、AI のトークン消費を減らせるかもしれません。

AI-DLC の価値は、開発が速くなることだけではありません。エンジニアが、プロダクトの価値、ドメインモデリング、アーキテクチャ、意思決定により多くの時間を使えるようになることにもあります。

一番の学びは、AI で実装を自動化するだけでは足りない、ということです。アーキテクチャの知識が失われず、大事な設計上の制約が守られるように、開発プロセスそのものを設計する必要があります。

## VM とコンテナが混在する環境での自己修復アーキテクチャ

**Seontaek Noh、Nobuyuki Morimoto（ZEAL）**

VM とコンテナが混在する環境で、自動復旧、AI による診断の支援、人による判断を組み合わせた自己修復アーキテクチャが紹介されました。

### 学びと考えたこと

- 障害対応は、自動復旧、AI による診断の支援、人による判断の3つの層に分けられます。
- 特に面白かったのは、ビジネスへの影響、SLO（サービスレベル目標）、復旧操作を元に戻せるかどうか、をもとにした判断の枠組みです。
- どこまで自動化するのが適切かは、技術的にできるかどうかだけでなく、復旧操作を誤ったときに何が起きるかでも決まります。
- 障害を意図的に注入（フォールトインジェクション）して、復旧率、平均復旧時間（MTTR）、AI による診断の効果を評価できないか、とも考えました。
- 目指すのは、すべてを自動化することではありません。どの責務なら、システムや AI に安全に任せられるかを見極めることです。

一番の学びは、自動化を設計するとは、その境界を設計し、人の判断を残すべき場所を決めることでもある、ということです。

## 認証・認可基盤の内製：事業の成長を支えるアーキテクチャ

**Makoto Fuchiwaki（日経）、Takayuki Kurata（freee）、Kazuya Shida（Linc'well）、Tatsuo Kudo（Authlete）**

このパネルディスカッションでは、各社が事業と技術の要件に応じて、内製と外部サービスを組み合わせながら認証・認可基盤をどう設計しているかが議論されました。

### 学びと考えたこと

- 認証・認可基盤は、「すべて自社で作る」か「すべて買う」かの二択ではありません。部品ごとに判断できます。
- Authlete は、OAuth と OpenID Connect のプロトコル処理やトークン管理を API として提供しています。そのため、各社は自社の認証ロジックやユーザー体験を自分たちで握ったままにできる、ということを知りました。
- 特に印象に残ったのは日経の事例です。高凝集・疎結合なソフトウェアは変更しやすい、ということは『Clean Architecture』で学んでいました。このセッションで、これらの原則は、部品を切り出して外部サービスに置き換えたり、逆に内製に戻したりするのも容易にする、という新しい見方を得ました。
- freee の事例からは、アーキテクチャの判断が組織の課題の解決にもつながると気づきました。専門性の高い機能を外部サービスに任せれば、社内の希少な専門家への依存を減らせ、メンバーが入れ替わってもシステムを保守しやすくなります。
- Linc'well の事例は、外部サービスと内製を組み合わせることで、複数のプロダクトで一貫したユーザー体験を提供できることを示していました。

一番の学びは、良いアーキテクチャは、ソフトウェアの設計だけでなく、事業の判断、リソースの配分、組織の変化にも柔軟性をもたらす、ということです。

高凝集・疎結合であることは、技術の変化にも、人の入れ替わりにも組織が適応する助けになります。

## AI 時代のデータプロダクト：オーナー主導のセルフサービス型データ基盤の設計

**Yuya Matsubara（NTT ドコモ）**

NTT ドコモが進めている、集中型のデータ基盤からデータメッシュへの移行が紹介されました。ドメインによるオーナーシップ、セルフサービスの基盤、AI を活用したデータエンジニアリングが主なテーマです。

### 学びと考えたこと

- データの量や使い道が増えると、中央のデータチームがボトルネックになります。これは技術の問題であると同時に、組織の問題でもあります。
- データメッシュでは、データを生み出し、その意味を理解しているドメインに責任を移します。データはプロダクトとして扱い、オーナー、品質基準、ビジネス上の文脈をはっきりさせるべきです。
- 利用者が不要な物理コピーを作らずに共有データにアクセスできる、ゼロコピーのデータ共有について知りました。Apache Iceberg のようなオープンなテーブルフォーマットが、データ基盤どうしの相互運用性を高める役割についても学びました。
- 特に面白かったのは、インセンティブが大事だという話です。オーナーを決めるだけでは不十分で、データが生み出した価値に対して、オーナーが評価される仕組みも必要です。
- 中央のデータチームの役割は、自分たちでデータを加工することから、セルフサービスの基盤と共通のガバナンス基準を通して各ドメインを支えることへと変わります。
- AI はデータエンジニアリングの負担を減らせます。一方で、信頼性を保つには、結果が一意に決まる CI のチェックと人の承認が役立ちます。
- オントロジーを使うと、業務の用語、データ、ワークフロー、判断のルールを結びつけられます。これが AI により豊かな文脈を与え、さらなる自動化につながることも知りました。

一番の学びは、スケールするデータ基盤をつくるには、技術だけでなく、組織の責任分担やインセンティブまで設計する必要がある、ということです。

AI 時代には、よく整理されたデータとビジネス上の文脈の価値が、さらに高まっています。

## 顧客ごとにではなく、顧客とともにつくる：マルチテナント SaaS の組織と設計

**Yuki Ozasa（株式会社アンチパターン CEO & VPoE）**

SaaS 企業が、顧客ごとの個別開発に陥らずに、顧客と深く協働するにはどうすればよいか。SaaSus Platform を開発してきた経験をもとに、Forward Deployed Engineering（FDE）、プロダクトの意思決定、組織設計、マルチテナントのアーキテクチャについて話されました。

### 学びと考えたこと

- AI で機能をより速く、安くつくれるようになっても、信頼性やセキュリティを確保し、長く運用し続けるためのコストと責任は残ります。
- Forward Deployed Engineer とプロダクトエンジニアは、互いを補い合う関係です。FDE は顧客のニーズを見つけて検証し、プロダクトチームはその気づきを、再利用できるプロダクトの機能に変えます。
- 個々の顧客の要望に寄りすぎると過剰なカスタマイズに陥り、理想のプロダクトに寄りすぎると市場とのずれが生まれます。
- 特に面白かったのが、ダイナミック・リチーミングという考え方です。プロダクトエンジニアが顧客の案件に直接関わることで、顧客の課題や、自分たちのプロダクトが現場でどう価値を生んでいるかを理解できます。
- 顧客ごとの要件には、共通のコアプロダクトを保ったまま、設定、公開 API、拡張機能、別の実装などで対応できます。
- SaaSus Platform の、計算資源は共有しつつテナントのデータは AWS アカウント単位で分離する方式を通して、ブリッジモデルのアーキテクチャを知りました。
- 価格と利用できる機能（エンタイトルメント）を切り離し、フィーチャーフラグを使えば、顧客ごとにコードベースを分けずに柔軟性を保てます。

一番の学びは、顧客とともにつくるとは、要望をすべて実装することではない、ということです。その奥にある課題を理解し、持続可能なプロダクトの価値に変えることです。

## C4 モデル：人と AI エージェントが同じ理解を持つために

**Simon Brown**

基調講演では、C4 モデル、Diagrams as Code、Models as Code、ADR（Architecture Decision Records）を使って、ソフトウェアアーキテクチャをうまく伝える方法が紹介されました。

これらを使えば、システムの構造、境界、アーキテクチャ上の判断について、人と AI エージェントが同じ理解を持てるようになります。

### 学びと考えたこと

- アーキテクチャ上の判断がどれほど重要かは、それを後から変えるコストで測れる、という見方を知りました。アーキテクチャ図は、判断を伝えるだけでなく、判断を下す助けにもなります。
- C4 モデルはこのセッションで初めて知りました。地図をズームイン・ズームアウトするというたとえが、特に気に入りました。私はアーキテクチャ図を描くときに、抽象度の違うものを混ぜてしまうことがあるので、ビューを分けるという考え方は大きな気づきでした。
- Diagrams as Code と Models as Code の違いを知りました。Structurizr のようなツールを使えば、1つのアーキテクチャモデルから複数のビューを生成でき、一貫性を保ちやすくなります。
- 図のほかに、arc42 と Simon Brown の Software Guidebook についても知りました。どちらも、アーキテクチャの背景、設計原則、制約など、ソースコードだけからは読み取りにくい知識を文書にするための方法です。
- テキストで書いたアーキテクチャモデルやドキュメントは、ソースコードと一緒に保守し、バージョン管理でき、AI エージェントからも読めます。
- ドキュメント、図、ADR、AGENTS.md を組み合わせれば、人と AI エージェントがシステムについて同じ理解を持てるようになります。
- アーキテクチャ適応度関数（fitness functions）を使えば、実装が決めたアーキテクチャ特性や制約を満たしているかを、継続的に確かめられます。

一番の学びは、アーキテクチャとはシステムを設計することだけではない、ということです。アーキテクチャの知識を、人にとっても AI エージェントにとっても、明示的で、共有でき、検証できるものにすることでもあります。

## おわりに

カンファレンス全体を通して、繰り返し現れるテーマがいくつかありました。

- 変化に適応できるシステムを設計すること

- 責務、インターフェース、境界をはっきりさせること
